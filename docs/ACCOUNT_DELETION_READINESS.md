# Account deletion initiation readiness

Catbird Lite now has an Account Deletion Options entry in Account Settings. It reviews permanent provider deletion and opens the official Bluesky account-settings page without collecting a password or requesting a deletion email. The handoff is separate from existing deactivation, sign-out and device account removal. It is a reviewable launch-gap proposal, not a claim that all account/data-deletion requirements are satisfied. Catbird-held server data deletion and native app qualification remain open.

The governing release scope is the [Catbird Lite App Store plan](/Users/joshlacalamito/Developer/Catbird+Petrel/docs/execution-plans/2026-09-29-catbird-1.0-app-store-plan.md). The factual gaps are in the [legal source audit](/Users/joshlacalamito/Documents/Codex/2026-10-03/task-8/legal-drafts/source-audit.md) and [launch review](/Users/joshlacalamito/Documents/Codex/2026-10-03/task-8/legal-drafts/launch-review.md). This proposal supersedes that plan's unverified suggestion to collect deletion credentials through Nest. It does not modify the privacy manifest, backend, website, existing deactivation or logout behavior.

## Supported completion route and limits

Apple requires an easy-to-find initiation option when an app supports account creation, permanent account/data deletion rather than deactivation alone, and a direct completion-page link when a website is needed. Reauthentication and intentional confirmation are allowed. Ordinary apps cannot require email/phone support as the completion path. Apple also requires honest information about delayed deletion. Its guidance describes a page on the developer's website; applying the provider-owned page arrangement to this independent client remains an App Review/product question. This implementation alone does not establish acceptance. [Apple account-deletion guidance](https://developer.apple.com/support/offering-account-deletion-in-your-app/).

The supported public route is `https://bsky.app/settings/account`. The official [route table](https://github.com/bluesky-social/social-app/blob/5b88335bb118f4f65dcb564e10109d6c6a78cb67/src/routes.ts#L56) maps AccountSettings there. Its [account-settings screen](https://github.com/bluesky-social/social-app/blob/5b88335bb118f4f65dcb564e10109d6c6a78cb67/src/screens/Settings/AccountSettings.tsx#L186) exposes Delete account alongside Deactivate account. This page contains the deletion control; no public route directly opening the dialog was found. Navigation requires sign-in. An unauthenticated web-tool read returned the JavaScript shell, not a verified signed-in screen or completion.

The provider's [deletion dialog](https://github.com/bluesky-social/social-app/blob/5b88335bb118f4f65dcb564e10109d6c6a78cb67/src/screens/Settings/components/DeleteAccountDialog.tsx#L85) explicitly requests the email code, collects the code/password, adds final confirmation, notifies the chat service, then deletes the PDS account and removes the local provider session. Credentials remain in the provider's flow. Catbird neither executes nor reproduces these calls.

The [request-account-delete Lexicon](https://github.com/bluesky-social/atproto/blob/main/lexicons/com/atproto/server/requestAccountDelete.json) is an email initiation procedure. More decisively, its [reference PDS implementation](https://github.com/bluesky-social/atproto/blob/0e1042e65d5df27030849167773728b84d469182/packages/pds/src/api/com/atproto/server/requestAccountDelete.ts#L24) rejects OAuth credentials for the endpoint, so adding a gateway permission cannot make the reference flow work. The [delete-account Lexicon](https://github.com/bluesky-social/atproto/blob/main/lexicons/com/atproto/server/deleteAccount.json) requires DID, password and token; the [PDS implementation](https://github.com/bluesky-social/atproto/blob/0e1042e65d5df27030849167773728b84d469182/packages/pds/src/api/com/atproto/server/deleteAccount.ts#L46) validates the password/email token and deletes account/storage. Lexicon descriptions alone do not prove compatibility with Catbird's OAuth session. Native password-token collection would introduce an additional sensitive credential flow, not a small routing fix.

AT Protocol documents Nest's general confidential-client/BFF architecture as a supported OAuth pattern; this is not evidence that deletion accepts those credentials. Its transitional generic scope excludes account-management actions. [AT Protocol OAuth specification](https://atproto.com/specs/oauth). Nest's stored source has no dedicated general Catbird-data purge flow identified in the legal audit; gateway logout removes/revokes the sign-in session and marks push authorization revoked, with a retry record for failed upstream revocation (`catbird/src/handlers/atproto.rs:1119–1196`). That is different from deleting every retained record.

## Different actions

| Action | Effect | New implementation |
| --- | --- | --- |
| Remove account from Catbird / sign out | Disconnects/removes local sign-in state and invokes existing gateway cleanup; does not establish deletion of all local caches or server records | Described only; not invoked |
| Delete Catbird-held data/session records | Needs defined coverage of sessions, push records, delivery/replay metadata, diagnostics, logs and backups, with lawful retention and completion evidence | Explicitly not requested by this flow; launch gap remains |
| Deactivate provider account | Existing reversible provider deactivation (`deleteAfter: nil`) and reactivation | Unchanged |
| Delete Bluesky/PDS account | Provider-owned irreversible code/password/final-confirmation flow; affects other apps using that identity | Direct account-settings handoff only |
| Delete Bluesky chat account | Chat-specific service action; not a replacement for PDS account deletion | Unchanged; official provider flow coordinates both |

## Federated provider coverage

The official PDS [self-hosting instructions](https://github.com/bluesky-social/pds/blob/main/README.md#using-the-bluesky-app-with-your-pds) support connecting Bluesky to a custom PDS. The official dialog uses the signed-in PDS client, not a hardcoded bsky.social deletion API. This supports offering the same settings route to Bluesky-hosted and compatible federated accounts. Handles do not reliably identify hosting providers, so no host inference or guessed `/delete` path is used.

The sheet explains custom-provider sign-in and explicitly identifies an unsupported case: if Bluesky cannot manage that account, the user must use the hosting provider's documented deletion process. This is an honest limitation, not a verified direct fallback or a claim of complete coverage. No provider website is guessed, no support email is presented as compliant deletion initiation, and no third-party PDS was contacted.

Unverified cases include non-reference PDS software with different deletion semantics, unavailable SMTP/email access, changed provider UI/routes, account takedown restrictions, and a provider which cannot be signed into through Bluesky. The browser or Bluesky app can already have another account signed in. The fixed URL carries no DID, handle, session, password or token and cannot bind that external session to Catbird's account. The UI shows the captured DID/matching handle and instructs users to verify the provider account before sending a code or confirming deletion. The provider performs the security confirmation.

## Local behavior and recovery

The entry remains visible while the account-details read is loading or fails. The sheet captures its target account once; an account switch/sign-out invalidates the handoff and requires cancel/reopen. Repeated taps are blocked while the OS processes a URL request. A rejected open can be retried, and the exact URL is selectable for manual browser use. A late completion after cancellation/account change cannot update the sheet.

The sheet routes through SwiftUI's system URL action, avoiding Catbird's internal bsky.app settings router. Cancel and swipe dismissal remain available. Returning from the provider does not sign out, clear data or claim successful deletion. OS acceptance reports only that the link opened, not that a page loaded or deletion finished. The link may open the browser or the installed Bluesky app according to system handling.

## Precise remaining decisions and acceptance work

1. **Provider completion approach:** provisionally retain this direct provider handoff. The alternative is a separately designed credential/confirmation flow in Catbird; it requires explicit credential-custody review and confirmed PDS support, not broader OAuth scopes. Resolve whether the provider-owned completion arrangement meets the app's product and App Review obligations before submission.
2. **Catbird-held data:** choose an authenticated in-app deletion-request endpoint with durable acknowledgement and a purge worker, or an authenticated Catbird-owned web completion page linked directly from the app. A manual worker is possible if users can initiate without support email/phone and receive truthful timing/completion confirmation. Recommended: authenticated durable request bound to DID, followed by reviewed dataset-specific deletion and a receipt. Define cross-device scope, permitted retained delivery/replay safeguards, telemetry-provider erasure, logs/backups, retention deadlines and request cancellation before enabling it. Current code does not implement or promise this.
3. **Unsupported providers:** verify the reference-PDS federated path and identify any additional provider-owned direct completion URLs from authoritative documentation. If no usable flow exists, this remains an explicit launch blocker for those accounts; contact instructions or reversible deactivation cannot be counted as its resolution. Changing supported providers/signup is a separate product decision and does not itself settle existing-account/data obligations.
4. **Finite owner qualification:** integrate this sealed proposal into a newly bound candidate, compile the native app under the owner's slot, then capture the sheet at large text/VoiceOver and test cancel, opening rejection and account switch with a fake opener. Use a provider session only to inspect the account page under explicit authorization; do not press Send email or any deletion confirmation. Actual destructive end-to-end deletion requires a separate authorized disposable-account exercise and is outside this task.

The provider-link choice is provisional and reversible before integration. Override it by withholding this change or replacing the fixed handoff after the new completion contract is verified. Full account/data-deletion readiness must remain open until the separate Catbird records process and provider coverage are substantiated.
